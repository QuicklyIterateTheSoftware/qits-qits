# Full network request/response capture for workspaces and CI daemons

Status: **implementation plan — no implementation has started.**

## 1. Outcome and boundary

Every HTTP request made by a workspace container or CI step container has one of two outcomes:

1. it goes directly to an explicitly internal QITS service, principally `qits-artifacts`; or
2. it goes through `qits-proxy`, which durably records the complete request and response and
   associates them with the workspace or CI run that caused them.

A direct Internet connection has no route. This is an observability invariant, not a hostile-code
sandbox: its purpose is to make dependency leakage obvious and diagnosable — for example, to show
the exact Maven POM or npm tarball fetched from the public Internet instead of `qits-artifacts`.

The feature covers HTTP/1.1, HTTP/2, HTTPS after TLS interception, WebSocket handshakes and frames,
and explicit HTTP-proxy tunnels. DNS lookups and non-HTTP protocols are recorded as denied
connection metadata, not invented as HTTP requests. Docker image pulls and Dockerfile build traffic
originate in dockerd/BuildKit rather than the invoking container; they form a separate capture plane
in section 8.

“Complete” means no normal size truncation or sampling: method, original URL, headers, trailers, raw
request body, response status, headers, trailers, raw response body, timing, and terminal outcome
are retained. Content encoding is preserved; a decoded preview may be derived later but never
replaces the captured bytes. Long-lived and unbounded streams are stored incrementally in chunks.
The proxy must apply backpressure and fail the request if durable capture cannot keep up — it must
never silently forward bytes that it failed to record.

## 2. Settled architecture

Add a deployable `services/qits-proxy` with two deliberately separate parts in one repository:

- **capture proxy** — a mature forward-proxy/TLS-interception engine with a small QITS integration
  layer; do not implement HTTP parsing, CONNECT, certificate synthesis, or HTTP/2 from scratch;
- **capture store/API** — metadata in its own database, byte bodies and frame streams in a
  content-addressed blob store, and authenticated read/delete APIs.

The first implementation should use mitmproxy as the capture engine. Its addon API supplies flow
lifecycle callbacks, raw bodies, WebSocket messages, connection metadata, and streaming controls.
Pin the engine version in the image, own the addon and persistence protocol in qits-proxy, and put
an adapter boundary around mitmproxy objects so the stored contract is not its serialization
format. Do not use mitmproxy's dump files as the product database.

The service has three listeners:

- an explicit forward-proxy listener reachable only from workload networks;
- a read API reachable from the platform network/gateway;
- an internal ingest interface between capture workers and the store, not gateway-routed.

The capture store owns its data. `qits-artifacts` remains the package/image repository and is not
turned into a generic packet archive. `qits-observability` may link to captures later, but it does
not own this high-volume, security-sensitive data.

For local Docker one qits-proxy container can contain both parts. For Swarm, capture workers may be
replicated while the store/API initially remains a constrained singleton with durable storage. The
ingest contract must make that split possible without changing the capture schema.

## 3. Durable capture model

Use an immutable session model. IDs are generated by the store, and timestamps used for ordering
are stamped by the capture worker rather than accepted from the workload.

### 3.1 Identity

`capture_principal` identifies one launched workload:

- kind: `CI_STEP`, `WORKSPACE`, `DOCKER_ENGINE`, or `BUILDKIT`;
- opaque principal ID and short-lived proxy credential hash;
- CI run ID, step index, repository ID and commit SHA where applicable;
- workspace database ID, workspace label and repository ID where applicable;
- container/task ID, node ID and launch/expiry timestamps.

CI and workspace launchers mint a random, single-container proxy credential, register only its hash
and attribution with qits-proxy, and inject the credential in the proxy URL. The clear credential is
never stored. Source IP is diagnostic metadata, not identity; overlay addresses and Swarm tasks are
ephemeral.

### 3.2 HTTP flow

`capture_flow` records principal, scheme, authority, method, exact URL, HTTP version, request start,
request-complete, response-first-byte, response-complete, client/server socket addresses, TLS
version/cipher/SNI/ALPN, response status, byte counts, and one terminal outcome (`COMPLETE`,
`CLIENT_ABORT`, `UPSTREAM_ERROR`, `CAPTURE_ERROR`, `DENIED`). Repeated ordered header and trailer
rows preserve duplicates and original values; do not collapse them into a map.

Request and response bodies are ordered chunk manifests over content-addressed blobs. A chunk is
committed before it is released downstream. This provides bounded memory, deduplication, recovery
after worker death, exact reconstruction, and support for bodies larger than a database LOB. Store
the raw entity bytes as observed on each HTTP side and record content encoding. Hash the complete
request and response streams as they close.

WebSockets use the HTTP upgrade flow plus ordered frame rows containing direction, opcode, flags,
timestamp, payload blob, and close information. HTTP streaming responses use the same body chunks;
an open flow is readable as an explicitly incomplete prefix.

CONNECT attempts that cannot be intercepted still get a flow containing principal, authority,
timing and failure reason. They never masquerade as full captures.

### 3.3 Secrets and lifecycle

Full capture necessarily stores authorization headers, cookies, tokens, source archives and API
responses. Preserve the original bytes because diagnosis is the feature; redaction is a derived
read/view concern, not destructive ingestion. Encrypt capture blobs and sensitive metadata at rest
with a dedicated key supplied as a Docker/Swarm secret. API list/search responses omit bodies and
secret header values by default; an explicit detail/download operation returns originals and is
audited.

Ship a configurable retention period and total-byte ceiling from day one. Retention deletion is by
whole flow, transactionally removing metadata and then reclaiming unreferenced blobs. When the
ceiling is reached and nothing eligible can be expired, new external requests fail closed with a
clear proxy error and `CAPTURE_ERROR`; they are not forwarded uncaptured. A startup reconciliation
repairs incomplete manifests and orphaned staged chunks after a crash.

## 4. TLS interception and trust

qits-proxy owns a private interception CA. Generate it during platform bootstrap, persist it outside
the container, and mount the private key only into capture workers. Publish the certificate (never
the private key) from an internal bootstrap endpoint and bake or install it into every supported
workspace/CI base image.

Install the CA in all trust paths actually used by the shipped images:

- operating-system CA bundle;
- Java trust store used by Maven/Gradle and JVM tools;
- Node/npm trust configuration;
- Python/pip trust configuration;
- Git/curl/OpenSSL defaults.

Do not disable TLS verification. Add an image conformance test that reaches an HTTPS fixture through
qits-proxy from every platform base image and proves that the stored request and response bodies are
byte-identical. Add a negative test with the CA absent so a silently disabled verifier cannot pass.

The proxy must reject unauthenticated use and must not become an open relay. Disable UDP egress from
workload networks so HTTP/3 cannot bypass the TCP proxy. Certificate-pinned or mutual-TLS clients
will fail and be represented honestly as failed CONNECT/TLS flows; supporting them requires an
explicit per-destination decision, not global verification bypass.

## 5. Workload networking

Replace the single shared workload attachment with two internal networks:

- `qits-ci-daemons` for CI step containers;
- `qits-workspace-daemons` for workspace containers.

Both contain qits-proxy and the internal services each workload must reach. `qits-artifacts` joins
both. CI control (`qits-ci`) joins the CI network; workspace control (`qits-workspaces`) joins the
workspace network. Keep the ordinary platform service network separate. Only qits-proxy also joins
an egress-capable network.

The networks are Docker bridge networks locally and `internal: true`, attachable overlay networks
in Swarm. Workloads receive uppercase and lowercase `HTTP_PROXY`/`HTTPS_PROXY` variables and a
minimal `NO_PROXY` containing exact internal service names and loopback. Never put domain suffixes,
CIDR-wide ranges, or the gateway in `NO_PROXY`: an overly broad exclusion recreates invisible
egress.

Docker embedded DNS remains available. Host firewall logging records attempted direct external TCP
or UDP connections as `direct-egress-denied` events associated as far as container/task metadata
allows. Those records contain no fictional payload.

Internal QITS calls intentionally bypass capture in the first release. `qits-artifacts` access
tracking is the positive evidence that the intended repository was used; qits-proxy is the evidence
and explanation when an external source was used.

## 6. Launcher integration

### 6.1 CI

Extend qits-ci's launch sequence before `docker run`:

1. register a `CI_STEP` principal with qits-proxy;
2. receive the one-use/short-lived proxy credential;
3. join the container to `qits-ci-daemons` instead of `qits-net`;
4. inject proxy variables, the CA path, and a non-secret capture principal ID;
5. revoke the credential when the step reaches a terminal state, including cancellation and failed
   daemon registration.

Registration failure fails the step before launch. Reaping a container must not delete its capture;
the run record stores the principal ID so its UI/API can link to flows.

### 6.2 Workspaces

Perform the same registration when qits-workspaces creates a workspace container, using its stable
database ID rather than the reusable branch-derived label. A workspace principal lives for the
container incarnation, not forever: recreate mints a new one, while the workspace view queries all
principals belonging to the workspace.

The workspace daemon and every child process inherit proxy configuration. Service definitions that
replace the environment must be amended to preserve the proxy variables explicitly. Stop/recreate
revokes the old credential after the container is no longer running.

## 7. Query API and user diagnosis

Provide machine-authenticated internal registration/revocation endpoints and user-authenticated read
endpoints under `/proxy/api`:

- list flows by principal, workspace, CI run/step, repository, time, host, method, status and
  outcome;
- fetch one flow's metadata, ordered headers and body manifests;
- stream the exact request or response body;
- list/reconstruct WebSocket frames;
- delete one capture or all captures before a time, subject to authorization;
- report store usage, retention state, incomplete flows and capture failures.

Lists must remain metadata-only and paginated; body bytes are fetched only on demand. Add links from
the CI run/step view and workspace telemetry view. The first UI can be a flow table and detail page:
timing, attribution, exact URL, headers with secrets visually masked by default, text/hex body
viewer, download-original actions, response status, and a conspicuous incomplete/failed state.

Add a derived `artifact-leak` classification for known public registries (Maven Central, npmjs,
PyPI, Docker Hub, Quay, GHCR and configurable additions). Classification never changes capture;
unknown destinations remain searchable instead of being discarded. A later CI policy may fail on
that classification, but enforcement is not part of the first delivery.

## 8. dockerd and BuildKit capture

Calls through the mounted Docker socket execute in the host daemon's network namespace. Swarm also
pulls task images from its nodes. Workload proxy variables cannot capture either path.

Treat each Docker/BuildKit worker as its own authenticated proxy principal. Configure dockerd's
daemon proxy and BuildKit worker proxy to qits-proxy, install the interception CA in their trust
stores, and keep qits-artifacts registry addresses in their exact `NO_PROXY`. Record node and builder
identity on every flow. Correlate to a CI run using Docker event/build lifecycle timestamps and the
existing CI run labels; where a shared daemon has overlapping builds, display the engine capture as
node-attributed and “possibly related” rather than claiming false exact attribution.

Precise build attribution requires one BuildKit worker/session principal per build. Make that the
Swarm target architecture: CI submits builds to a managed builder service which mints a per-build
proxy identity. Until then, node-level capture still detects the invariant that a public registry
or package source was contacted.

The local bootstrap is a declared exception: it pulls images before qits-proxy and qits-artifacts
exist. Mark bootstrap traffic out of scope rather than implying it was captured.

## 9. Swarm shape

Create the networks and secrets as deployment resources rather than relying on Compose-created
bridge state. Place capture workers only on labelled egress nodes. Workload nodes have no default
external forwarding path for the internal overlays; host firewall rules allow proxy-node egress and
log rejected workload/node attempts.

Do not publish the forward-proxy port through Swarm's routing mesh. It is reachable only by service
DNS on the internal overlays. Publish the read API only through qits-gateway. Use encrypted overlays
for captured plaintext in transit between capture workers and the store.

The singleton store is acceptable for the initial Swarm deployment but must use durable node-pinned
storage and placement constraints. Before adding replicas, move blobs to shared/object storage and
prove idempotent ingest, chunk deduplication, flow ownership during worker loss, and CA-key
distribution. Replication without those prerequisites would create partial captures.

## 10. Delivery workstreams

### A. Contract and fixture

- Create `services/qits-proxy`, its AGENTS/README, schemas, persistence ports and a deterministic
  upstream fixture covering HTTP, HTTPS, duplicate headers, request/response trailers, compressed
  bodies, multi-gigabyte generated streams, aborts, HTTP/2 and WebSockets.
- Freeze the stored/API contract with reconstruction tests proving byte equality.
- Define capture failure semantics before any real workload is routed through it.

### B. Capture engine and store

- Package pinned mitmproxy plus the QITS addon and adapter.
- Implement authenticated principal lifecycle, chunk-before-forward persistence, recovery,
  encryption, retention, capacity fail-closed behavior, and health/metrics.
- Prove that killing the worker or store mid-request yields an explicit incomplete/failed flow and
  never an unrecorded successful transfer.

### C. TLS and base images

- Add bootstrap CA generation/persistence and Swarm secret/config equivalents.
- Install the public CA and proxy conformance tests in every workspace and CI base image.
- Verify common Maven, npm, Git, curl, pip and JVM requests against the HTTPS fixture.

### D. CI routing and attribution

- Add principal registration/revocation to qits-ci and change the step network.
- Inject proxy settings and keep exact internal QITS destinations in `NO_PROXY`.
- Add a real-container gate: a public-style Maven/npm fixture request is fully captured and linked
  to the exact run/step, while a qits-artifacts request bypasses the proxy.

### E. Workspace routing and attribution

- Add the equivalent lifecycle to qits-workspaces and preserve proxy configuration through daemon
  child/service launches.
- Add a real-container gate for exact workspace attribution, recreation, long-lived streams and
  credential revocation.

### F. Read surface and diagnosis UI

- Ship paginated search, exact-body download, audit records, store status and retention operations.
- Add CI-step and workspace links plus the flow detail UI and artifact-leak classification.
- Prove large bodies never enter list responses or browser memory unless explicitly opened.

### G. Docker/BuildKit plane

- Configure local worker daemon/builders through the proxy, excluding qits-artifacts exactly.
- Ingest Docker event correlation and render uncertainty honestly.
- Introduce per-build builder identities before claiming exact run attribution in Swarm.

### H. Swarm deployment and cutover

- Define internal overlay networks, egress placement, secrets, persistent volumes and firewall
  rules; deploy a canary proxy and one canary worker node.
- Run capture-only observation first, classify legitimate external traffic, then remove ordinary
  direct routes from all workload networks.
- Test worker rescheduling, proxy/store restart, certificate rotation, storage exhaustion and node
  loss before expanding beyond the canary.

## 11. Acceptance gates

The feature is complete only when all of the following are demonstrated end to end:

1. A CI step and a workspace each POST a unique binary body to an HTTPS fixture and receive a
   unique binary response; both directions reconstruct byte-for-byte from the store with the exact
   headers, URL, status and timestamps, attributed to the correct workload.
2. Concurrent workloads cannot exchange attribution, including after workspace recreation and
   Swarm task rescheduling.
3. Maven, npm, pip, Git and curl succeed through interception using normal certificate verification;
   the same images fail the negative test when the CA is removed.
4. Requests to qits-artifacts bypass qits-proxy and update qits-artifacts' own access evidence;
   requests to known public repositories appear as `artifact-leak` with their exact paths and
   payloads.
5. Direct TCP/UDP Internet access from the internal networks fails and produces denied-attempt
   metadata. Internal control WebSockets and artifact access continue to work.
6. A response larger than memory is captured under bounded memory, and a long-lived stream remains
   readable as ordered chunks without truncation.
7. Store outage, full disk, worker death and client/upstream aborts produce explicit terminal or
   incomplete records; no successful uncaptured forwarding is observed.
8. Docker/BuildKit public access is captured at least to the correct node/builder, and the UI does
   not overstate run attribution. A dedicated builder proves exact per-build attribution.
9. Retention deletes complete flows, reclaims only unreferenced blobs, and leaves an audited record
   of the deletion. CA rotation permits an overlap window and does not expose the private key to
   workloads.
10. The same behavioral suite passes against local Docker bridge networks and a multi-node Swarm
    canary using internal overlays.

## 12. Explicit non-goals for the first release

- pretending arbitrary UDP or non-HTTP TCP protocols have request/response semantics;
- silently bypassing capture for pinned-certificate or mutual-TLS destinations;
- automatic CI failure based on leak classification;
- packet-level capture of direct denied attempts;
- globally replicating the capture store before shared durable storage exists;
- capturing bootstrap pulls that necessarily happen before the platform proxy starts.
