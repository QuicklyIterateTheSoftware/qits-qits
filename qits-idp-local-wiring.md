# Wiring qits-idp into a platform

Phase 1 of qits-idp-plan.md, from the deployment side: what the idp needs, what
each consumer needs, and the order in which a running platform may be given it.

`qits-local-up.sh` already does all of this for a local bring-up — **the compose
file is generated by that script**, so the additions below are committed there,
not in `docker-compose.qits.yml` (which is machine-specific, gitignored state).
The snippet in this file is for hand-editing a compose file already on disk when
a full rerun is not wanted; a rerun regenerates it either way.

## What local-up does now

- `qits-idp` joins `CORE` (hand-built seed image) **and** `DEPLOYABLES` (a cd
  application, updated by a push like everything else). It deploys second, after
  observability: every later application's tokens come from it.
- A `qits-idp-data` volume at `/data`. The signing key lives in that database. An
  idp on ephemeral storage comes up healthy and mints a new keypair on every
  recreate, invalidating every token in flight silently — which is why the image
  refuses to boot without the datasource url.
- Client secrets are generated on first run and recorded in
  `.qits-bootstrap.env` (`IDP_SECRET_QITS_CI=…`). That file is now read *before*
  the build, not only on the skip-build path, so a full rerun keeps the secrets
  it issued last time. `QITS_IDP_CLIENT_<ID>_SECRET` pins one by hand.
- The idp gets no host port and no gateway route. Nothing outside qits-net talks
  to it in phase 1, and `/idp/token` behind the unauthenticated local gateway
  would be a token vending machine. Phase 3's user flows put it on the route
  table.
- The seed wait loop waits for the idp first, and the script's replayed
  `build-succeeded` now carries a bearer (it borrows qits-ci's client — that
  event stands in for the announcement qits-ci never sent).
- Both places that configure a container are updated together: the compose seed
  **and** `qits.cd.run-args.<application>` in the cd-config volume. A run-args
  line left behind means the first cd redeploy silently drops enforcement.
- Both ENDS of every hop are configured together: the receiver's gate and the
  sender's `quarkus.oidc-client`, which is shipped disabled and posts bare
  until it is enabled.

## The gate: ON locally

`QITS_AUTH_MACHINE_REQUIRED=true` for qits-ci, qits-cd and qits-artifacts, and
`QUARKUS_OIDC_CLIENT_CLIENT_ENABLED=true` for the two that call out.
`QITS_MACHINE_AUTH=0` turns both off for a bring-up that wants the old
behaviour. **Every hop has two switches** — the receiver's gate and the sender's
oidc-client — and locally they move together. A deployment moves them
separately, which is what lets one hop be turned on at a time.

Safe because the boot order does not matter: the gate also switches the OIDC
tenant (`quarkus.oidc.tenant-enabled=${qits.auth.machine.required:false}` in all
three services), and with it on, discovery is off and `jwks-path` is configured,
so nothing is fetched at startup and a service that boots before the idp is
fine. Only token *issuance* needs the idp live, and the script waits for it
before the first push.

Two things had to be handled for it to hold:

- The script's own `POST /cd/api/events/build-succeeded` needed a token.
- qits-artifacts needs `CLAIMS_PROJECT=*`: the git host announces pushes for
  every repo, and qits-ci's intake checks the token's `project` claim against the
  repo the event names.

Nothing else in the platform calls a guarded endpoint. qits-projects and
qits-workspaces reach the git origins through the shared volume, not through
artifacts' JSON API; qits-ci only *reads* `/artifacts/api/repositories`; the
registry (`/v2`), the git host (`/artifacts/git`) and npm are untouched in phase
1. The artifacts SPA is a read-only explorer, so no user-facing button breaks.

The consequence to know: artifacts' admin writes stop accepting *user* traffic.
`MachineAuth` demands a machine token, and a forward-auth browser identity is not
one. That is the contract's intent — those endpoints were always a system API —
but it means `PUT /artifacts/api/repositories/…` from a browser now needs a
bearer.

## Env matrix

`<secret>` is the value recorded for that client in `.qits-bootstrap.env`.

| Var | Container | Example |
|---|---|---|
| `QUARKUS_DATASOURCE_IDP_JDBC_URL` | qits-idp | `jdbc:h2:file:/data/idp/h2/idp` (needs `qits-idp-data:/data`) |
| `QITS_IDP_ISSUER` | qits-idp | `http://qits-idp:8080/idp` |
| `QITS_IDP_CLIENT_QITS_CI_SECRET` | qits-idp | `<ci secret>` |
| `QITS_IDP_CLIENT_QITS_CD_SECRET` | qits-idp | `<cd secret>` |
| `QITS_IDP_CLIENT_QITS_ARTIFACTS_SECRET` | qits-idp | `<artifacts secret>` |
| `QITS_IDP_CLIENT_QITS_WORKSPACES_SECRET` | qits-idp | `<workspaces secret>` (unused until phase 2) |
| `QITS_IDP_CLIENT_QITS_GATEWAY_SECRET` | qits-idp | `<gateway secret>` (unused until phase 3) |
| `QITS_IDP_CLIENT_QITS_ARTIFACTS_CLAIMS_PROJECT` | qits-idp | `*` |
| `QITS_AUTH_MACHINE_REQUIRED` | qits-ci, qits-cd, qits-artifacts | `true` |
| `QUARKUS_OIDC_AUTH_SERVER_URL` | qits-ci, qits-cd, qits-artifacts | `http://qits-idp:8080/idp` |
| `QUARKUS_OIDC_CLIENT_CLIENT_ENABLED` | qits-ci, qits-artifacts | `true` |
| `QUARKUS_OIDC_CLIENT_AUTH_SERVER_URL` | qits-ci, qits-artifacts | `http://qits-idp:8080/idp` |
| `QUARKUS_OIDC_CLIENT_CREDENTIALS_SECRET` | qits-ci | `<ci secret>` |
| `QITS_ARTIFACTS_CLIENT_SECRET` | qits-artifacts | `<artifacts secret>` |

**`CLIENT_ENABLED` is the line this platform cannot do without.** Both services
ship `quarkus.oidc-client.client-enabled=false`, so an issuer address and a
secret are not enough — the client is never built and the POST goes out bare. Set
the gate without it and the git host's post-receive to qits-ci and ci's
build-succeeded to qits-cd both answer 401: CI stops on every push, and neither
side logs a reason (both calls are fire-and-forget).

Pair it with the secret always. A client enabled without one refuses to boot,
which is the intended failure — better than posting unauthenticated.

One secret spelling per service, and it is a fact about that service:
qits-artifacts interpolates `QITS_ARTIFACTS_CLIENT_SECRET` in its own
`application.properties`, while qits-ci names no placeholder at all, so the
canonical `QUARKUS_OIDC_CLIENT_CREDENTIALS_SECRET` carries it. (That canonical
name would override either one; there is no `QITS_CI_CLIENT_SECRET`.)

**Deliberately not set:**

- `qits.auth.machine.audience` — each service's own id, in its own
  `application.properties`. Turning the gate on without it fails at startup.
- Anything `QUARKUS_OIDC_*` on **qits-gateway**. The local variant is built
  unauthenticated; an auth-server-url would arm OIDC on it. Phase 3 owns that.
- Anything on **qits-workspaces**. Its clients are phase 2. It gets a secret at
  the idp so the client is usable the day its consumer arrives.
- qits-cd gets no oidc-client config: in phase 1 it calls no guarded endpoint, so
  its client exists and goes unused.

## Generating secrets

`head -c 32 /dev/urandom | sha256sum | cut -c1-32` — what the script uses.

Two rules:

1. **Stable across reruns.** Rotating a secret locks a service out until it is
   redeployed with the new value. The script records them and reuses them; a
   live platform keeps them wherever it keeps its other deployment config.
2. **The same string on both sides.** The idp's
   `QITS_IDP_CLIENT_<ID>_SECRET` and that service's oidc-client credential are
   one value in two places. A mismatch is `invalid_client` in the caller's log
   and nothing at all in the idp's.

Unlike `QITS_PUSH_TOKEN` these are real secrets: never typed by a human, never
named in docs, no reason to be guessable.

## Rollout on a live platform

The idp exists before anything depends on it, senders send before receivers
require, and each step is separately reversible.

1. **Secrets first.** Decide all five and put them where the platform's
   deployment config lives. Nothing reads them yet.
2. **Deploy qits-idp** with its volume, issuer, five secrets and the artifacts
   claim grant. Verify before going further:
   `curl $IDP/.well-known/openid-configuration`, `curl $IDP/jwks`, and one
   `curl -u qits-ci:<secret> -d grant_type=client_credentials -d audience=qits-cd
   $IDP/token`. A token that comes back and verifies against the JWKS is the gate
   on everything below.
3. **Deploy the consumers with the gate OFF and the senders ON** — issuer address
   and secrets in place, `QUARKUS_OIDC_CLIENT_CLIENT_ENABLED=true`,
   `QITS_AUTH_MACHINE_REQUIRED=false`. Senders now send bearers, receivers do not
   yet demand them. This is the safe intermediate state, and it is where a
   secret typo shows up as a log line instead of an outage. It exists only
   because the two switches are independent — flip them together and this step
   is not available.
4. **Flip the gate, one service at a time**, watching each before the next:
   qits-cd, then qits-ci, then qits-artifacts. Rollback is the env back to
   `false` and a redeploy — the code path is unchanged, the gate is read per
   call.
5. **Restart the idp once** and confirm previously issued tokens still verify.
   That is the volume doing its job; if they do not, the datasource url is wrong
   and step 2 has to be redone before anything else.

Two operational notes for the live platform:

- **Environment membership.** No longer a hazard: registration is derived from
  each repo's `.config/qits/deployments.yml` on a green build, and
  `qits-local-up.sh` reconciles the environment row by `PATCH` instead of
  recreating it. qits-idp is a singleton — it deploys from `main` and runs as
  `qits-cd-singleton-qits-idp-<id8>`.
- **Manual event replays now need a token.** The two documented recovery
  commands — replaying `POST /ci/api/events/post-receive` after a lost hook and
  `POST /cd/api/events/build-succeeded` after a write-wedge — answer 401 once
  the gate is on. Fetch a token first
  (`-u qits-ci:<secret>`, `audience=qits-ci` or `qits-cd`) and send it as
  `Authorization: Bearer`.

## Checked against the consumers

This was written before qits-ci, qits-cd and qits-artifacts had committed, so the
consumer side followed qits-auth-core's README. Read back against their files:

1. **Confirmed.** Each service sets `quarkus.oidc.auth-server-url`,
   `discovery-enabled=false`, `jwks-path=jwks`,
   `token.audience=${qits.auth.machine.audience}` and its own
   `qits.auth.machine.audience`. All three also set
   `quarkus.oidc.tenant-enabled=${qits.auth.machine.required:false}`, so the
   deployment overrides only the gate, the address and the secret.
2. **Corrected.** `quarkus.oidc-client.client-enabled` is shipped `false` and had
   to be added — see the matrix. There is no `QITS_CI_CLIENT_SECRET`; qits-ci
   takes the canonical `QUARKUS_OIDC_CLIENT_CREDENTIALS_SECRET`, qits-artifacts
   names `QITS_ARTIFACTS_CLIENT_SECRET` in its own file.
3. **Confirmed.** qits-ci's oidc-client asks for `audience=qits-cd` and
   qits-artifacts' for `audience=qits-ci`, both as grant options in their own
   files. The idp's shipped audience lists are wide, so nothing here narrows
   them.
4. **Confirmed, with one correction to the claim's name.** qits-ci matches the
   `project` claim against the event's **repoId** — it has no project entity —
   so `CLAIMS_PROJECT=*` for qits-artifacts is what covers every repository.
   Nothing else in the platform calls a newly guarded endpoint.

Also assumed: `services/qits-idp` carries no `.config/qits/ci-post-receive.yml`
yet, so the bootstrap overlays the standard publish step and commits it into its
own clone. The repo should grow its own.

## The compose snippet

For a `docker-compose.qits.yml` already on disk. Substitute the secrets.

```yaml
volumes:
  # THE SIGNING KEY LIVES HERE.
  qits-idp-data:
    name: qits-idp-data

services:
  qits-idp:
    image: qits/idp:latest
    container_name: qits-idp
    environment:
      QUARKUS_DATASOURCE_IDP_JDBC_URL: jdbc:h2:file:/data/idp/h2/idp
      QITS_IDP_ISSUER: http://qits-idp:8080/idp
      QITS_IDP_CLIENT_QITS_CI_SECRET: "<ci secret>"
      QITS_IDP_CLIENT_QITS_CD_SECRET: "<cd secret>"
      QITS_IDP_CLIENT_QITS_ARTIFACTS_SECRET: "<artifacts secret>"
      QITS_IDP_CLIENT_QITS_WORKSPACES_SECRET: "<workspaces secret>"
      QITS_IDP_CLIENT_QITS_GATEWAY_SECRET: "<gateway secret>"
      # The git host announces pushes for every repo.
      QITS_IDP_CLIENT_QITS_ARTIFACTS_CLAIMS_PROJECT: "*"
    volumes:
      - qits-idp-data:/data
    networks: [qits-net]
    restart: unless-stopped
```

Added to the `environment:` of the three consumers:

```yaml
  qits-ci:
    environment:
      QITS_AUTH_MACHINE_REQUIRED: "true"
      QUARKUS_OIDC_AUTH_SERVER_URL: http://qits-idp:8080/idp
      QUARKUS_OIDC_CLIENT_CLIENT_ENABLED: "true"
      QUARKUS_OIDC_CLIENT_AUTH_SERVER_URL: http://qits-idp:8080/idp
      QUARKUS_OIDC_CLIENT_CREDENTIALS_SECRET: "<ci secret>"

  qits-artifacts:
    environment:
      QITS_AUTH_MACHINE_REQUIRED: "true"
      QUARKUS_OIDC_AUTH_SERVER_URL: http://qits-idp:8080/idp
      QUARKUS_OIDC_CLIENT_CLIENT_ENABLED: "true"
      QUARKUS_OIDC_CLIENT_AUTH_SERVER_URL: http://qits-idp:8080/idp
      QITS_ARTIFACTS_CLIENT_SECRET: "<artifacts secret>"

  qits-cd:
    environment:
      QITS_AUTH_MACHINE_REQUIRED: "true"
      QUARKUS_OIDC_AUTH_SERVER_URL: http://qits-idp:8080/idp
```

And the matching cd run-args, in `config/application.properties` on the
`qits-cd-config` volume — a compose-only change lasts until the first redeploy:

```properties
qits.cd.run-args.qits-idp=-v qits-idp-data:/data \
  -e QUARKUS_DATASOURCE_IDP_JDBC_URL=jdbc:h2:file:/data/idp/h2/idp \
  -e QITS_IDP_ISSUER=http://qits-idp:8080/idp \
  -e QITS_IDP_CLIENT_QITS_CI_SECRET=<ci secret> \
  -e QITS_IDP_CLIENT_QITS_CD_SECRET=<cd secret> \
  -e QITS_IDP_CLIENT_QITS_ARTIFACTS_SECRET=<artifacts secret> \
  -e QITS_IDP_CLIENT_QITS_WORKSPACES_SECRET=<workspaces secret> \
  -e QITS_IDP_CLIENT_QITS_GATEWAY_SECRET=<gateway secret> \
  -e QITS_IDP_CLIENT_QITS_ARTIFACTS_CLAIMS_PROJECT=*
```

(One line in the real file — run-args are whitespace-split, and the continuations
above are for reading only.) The same `-e` flags go onto the existing
`qits.cd.run-args.qits-ci`, `…qits-cd` and `…qits-artifacts` lines.
